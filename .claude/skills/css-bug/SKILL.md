# css-bug

`$ARGUMENTS` の最初の語で、どの手順を行うかを決める。

- `status`: 「状態の更新」
- `submit`: 「送信の準備」
- `reported`: 「報告の記録」
- それ以外: 「調査」。引数全体がバグの説明

状態の値の定義は、リポジトリのルートの `README.md` の「状態の値」が正本。検索先ごとの手順と、報告文の欄の決め方は [trackers.md](trackers.md) にある。

トラッカーで行うのは、検索と閲覧だけ。報告の送信、サインイン、コメントの投稿はユーザーが行う。

## 調査

各段は、完了の条件を満たしてから次の段に進む。

1. **名前の確認**: 説明に出てくるプロパティ、値、機能の名前が仕様にあるかを確かめる。名前が違っていたり旧名だったりしたら、正しい名前と根拠をユーザーに示し、どの機能を調べるかの答えを待つ。
   完了: 調べる機能を、仕様にある正式な名前で言える。
2. **作成**: `node scripts/new-bug.mjs <slug> "<日本語の題>"` を実行する。slug は症状を表す短い英語にし、エンジンの名前は入れない。
   完了: `bugs/<slug>/README.md` と `bugs/<slug>/repro.html` がある。
3. **仕様**: この段の初めに、csswg-drafts の Issue と web-platform-tests の検索を tracker-searcher に1つ任せ、バックグラウンドで動かす（頼み方は「検索の任せ方」）。そのあいだに仕様の該当の節を読み、「期待する挙動と根拠」に節への直リンクを付けて書く。仕様がその挙動を決めているのか、UA に任せているのか、決めていないのかも書く。返ってきた Issue のうち関係しそうな件を開いて読み、議論中の件があれば書く。
   完了: 仕様の節への直リンクと、仕様が決めているかどうかの判断がある。
4. **テストケース**: `repro.html` を、説明の症状だけが出る最小の HTML にする。
   - 外部の資源を読まない。
   - 日本語などを含む要素には `lang` 属性を付ける。改行の処理が言語で変わるため。
   - 期待する見た目を別の手段で作った参照を、テストの横に並べる。目で見て一致するかどうかで判定できるようにするため。作れないときは、期待する見た目を文で書く。
   - アニメーションは、時点を止めて比べられるようにする（途中の時点を `animation-delay` の負の値で固定した複製を並べる、など）。
   完了: 症状に関係しない CSS を外しても、まだ症状が出る。
5. **ブラウザでの確認**: `node scripts/browser-versions.mjs` でバージョンを取る。先行版のバージョンが同じエンジンの安定版より古ければ、先行版を更新するようユーザーに頼み、更新を待ってから取り直す。`open -a "<アプリ名>" bugs/<slug>/repro.html` で各ブラウザに開く。機能が設定（`about:config`、`chrome://flags` など）で無効になっているなら、変える設定をユーザーに示す。
   ここで止まり、各ブラウザの見た目の判定をユーザーに尋ねる。判定はユーザーが行う。
   答えを「確認した環境」の表に書く。変えた設定も書く。
   完了: 入っているすべてのブラウザ（安定版と、Nightly、Canary、Technology Preview の先行版）の結果が表にある。
6. **web-platform-tests**: 手順 3 で任せた tracker-searcher が返したテストから、症状に該当するものを選び、各エンジンの結果を「web-platform-tests」に書く。テストが見つからなければ、探した場所（検索語）を書く。
   完了: テストの URL と結果か、探した場所がある。
7. **検索**: 期待どおりに動かなかったエンジンごとに tracker-searcher を1つずつ任せ、同時に動かす。返ってきた検索を、件数が0のものも含めてすべて「検索の記録」に書く。関係しそうな件は、自分で開いて中身を読む。
   完了: 1つのトラッカーにつき3つ以上の組み合わせで検索し、関係しそうな件をすべて開いて中身を読んだ。
8. **状態**: エンジンごとの `status.*` を決め、根拠を「結論」に書く。既存の報告があれば `links.*` にその URL を、仕様の節を `links.spec` に書き、`updated` を今日の日付にする。
   完了: frontmatter のすべての `status.*` が `-` 以外になり、「結論」がその理由を説明している。
9. **下書き**: `drafted` にしたエンジンごとに、`node scripts/new-report.mjs <slug> <engine>` で `bugs/<slug>/report.<engine>.en.md` を作り、英語で埋める。報告先と欄の値は trackers.md の手順で決める。
   埋めたら reviewer に、slug とエンジンだけを渡して確かめさせる。調査の経緯や、迷った点は渡さない。`changes` が返ったら指摘を直し、前回の判定を添えてもう一度渡す。2回直しても `approve` にならなければ止め、reviewer の指摘と自分の考えを並べてユーザーに見せる。提案（英語の直し案）を取り入れるかは自分で決める。Fable の利用の上限に達して reviewer を呼べないときは、呼び出しに `model: opus` を渡す（effort は xhigh）。
   完了: 冒頭のコメントの欄がすべて埋まり、本文の各節に内容があり、reviewer が `approve` を返した。
10. **コミット**: `node scripts/build-index.mjs` で一覧を作り直す。「公開前の点検」を行ってからコミットする。push はしない。
    完了: コミットができ、`git status` に変更が残っていない。

調査を終えたら、各エンジンの状態と、下書きがあればそのファイルを報告する。報告文はユーザーが送信する。

## 検索の任せ方

tracker-searcher には、次の3つを渡す。

- 検索先: WebKit Bugzilla、Mozilla Bugzilla、Chromium Issue Tracker、csswg-drafts、web-platform-tests のどれか（手順 3 の検索係には csswg-drafts と web-platform-tests の2つ）
- 検索語: 正式な名前、旧名、症状の語、関連する語の組み合わせ。トラッカー1つにつき3つ以上。web-platform-tests には、関係する仕様のディレクトリ（アニメーションの症状なら `css-animations` も）を含める
- 調べている機能の正式な名前と、症状を1文で。検索係が題に使われそうな別の形の語を足すときの手がかりになる

返ってくるのは検索ごとの件の一覧で、どの件が関係するかの判断は含まない。関係するかどうかは、件を開いて読んでから自分で決める。

## 状態の更新

`status` のときの手順。

1. `node scripts/bug-status.mjs` で、`links.*` にある Bugzilla の件の現在の状態を取る。`manual` に出た Chromium と GitHub の件は、組み込みブラウザで開いて確かめる。
2. 解決した件の状態を更新する。修正されたら `fixed` にし、直ったバージョンを「結論」に書く。重複として閉じられたら、統合先の件の URL（出力の `dupeOf`）を `links.*` に加える。あわせて `updated` を今日の日付にする。
3. 調査の手順の 10 と同じ方法で、一覧を作り直してコミットする。

## 送信の準備

`submit <slug> <engine>` のときの手順。`bugs/<slug>/report.<engine>.en.md` から、ユーザーがトラッカーのフォームにそのまま貼れる欄の値と本文を作る。各欄の値の取り方と本文の整え方は、trackers.md の「送信の準備」にある。

1. **公開 URL**: テストケースの公開 URL を組み込みブラウザで開き、ページが返るか確かめる。404 なら、コミットが Pages に出ていない（push、マージ、Pages の更新のどれかが済んでいない）。
   完了: 公開 URL が開けるか、開けない理由をユーザーに伝える準備ができている。
2. **欄の値**: トラッカーで今選べる値を取り、「確認した環境」に合う値を選ぶ。
   完了: trackers.md の欄の表のすべての欄に値がある。
3. **本文**: 下書きから、トラッカーの表示に合わせた Summary と Description を作る。下書きのファイルは変えない。
   完了: Summary と Description が、それぞれ1つのコードブロックで貼れる形になっている。
4. **提示**: フォームの URL、欄の表、Summary、Description を示す。添付するファイルを明記する。公開 URL が開けないときは、URL 欄を空にし、本文から公開 URL を外した Description を示して、理由を添える。

送信したら `reported` で記録するよう、最後に案内する。

## 報告の記録

`reported <slug> <engine> <URL>` のときの手順。`<engine>` は `webkit`、`gecko`、`blink` のどれか。

1. `bugs/<slug>/README.md` の `status.<engine>` を `reported` にし、`links.<engine>` に URL を加え、`updated` を今日の日付にする。
2. 「結論」に、報告した日と URL を書く。
3. 報告した件を読み、題、添付、See Also、本文の公開 URL が「送信の準備」で示したとおりかを確かめる。抜けや開けない URL があれば、ユーザーに伝える（直すのはユーザー）。
4. **報告文の差分**: 報告文を書くときの規則を、ユーザーの直しから育てる。次の2つの差分を見る。
   - git の差分: `git log --format=%H -- bugs/<slug>/report.<engine>.en.md` で下書きを最初に入れたコミットを探し、その時点の下書きと今の下書きを比べる。送信の前にユーザーが下書きを直した分が出る。
   - 送った本文との差分: 報告した件の最初のコメント（送った本文）を読み、今の下書きから trackers.md の「本文の整え方」で Markdown を外したものと比べる。フォームで直した分が出る。Bugzilla は件のページを組み込みブラウザで開き、同じオリジンから `/rest/bug/<ID>/comment` を読む。Chromium は件のページを読む。

   見つけた違いを「どの報告にも当てはまる傾向」「事実の修正」「その件だけのこと」に分ける。傾向は、trackers.md の「報告文の書き方」に足す規則の案にしてユーザーに示し、選ばれたものだけを足す。送った本文との違いは、Markdown を保ったまま下書きに反映する（下書きを送った本文で上書きしない）。違いがなければ、そう伝えて次に進む。
   完了: 2つの差分の違いをすべて3つのどれかに分け、選ばれた規則と、送った本文との違いが反映されている。
5. 調査の手順の 10 と同じ方法で、一覧を作り直してコミットする。

## 公開前の点検

このリポジトリは Public。コミットする前に `git diff --cached` を読み、公開してよい情報だけが入っていることを確かめる。

- 個人の情報（メールアドレス、氏名）がない。
- ローカルの絶対パスがない。リポジトリの中のファイルは相対パスで書く。
- このリポジトリの外のプロジェクトの名前がない。
